# Lampstand Project Technical Documentation

## Architecture

Lampstand Project is an Electron desktop application containing a React and TypeScript frontend and a local Node.js gateway.

- Electron serves the production frontend on `127.0.0.1:5173`.
- The unified local gateway runs on `127.0.0.1:9656`.
- A legacy API can be proxied from `127.0.0.1:9655`. The gateway answers Knowledge browsing itself and forwards only the paths it has not taken over; the three chat assistants are answered by the gateway directly and never reach it (see *Chat assistants*).
- Ollama normally runs on `127.0.0.1:11434`.
- Local Whisper normally runs on `127.0.0.1:8000`.
- Voice Studio, when the operator installs it, serves an OpenAI-compatible speech API on `127.0.0.1:3900`.
- Optional media providers use their separately configured local endpoints.

The application is local-first. Supabase supplies verified member identity and remote workspace policy; it is not the primary store for the bundled reading libraries.

## Project layout

- `src/` — React pages, components, stores, API clients, and styles.
- `server/` — local gateway, library readers, indexing routes, and provider integration.
- `desktop/` — Electron main process, preload bridge, service startup, and updater.
- `scripts/` — importers, indexing, OCR, translation, dependency setup, backup, and release preparation.
- `data/` — package-ready built-in libraries and definitions.
- `docs/` — user, installation, operational, and Supabase migration documentation.
- `release/` — generated Windows installer artifacts.

## Bundled library layout

The Windows installer packages `data/` as an Electron extra resource. Release preparation must provide:

- `data/hwmr-library.json`
- `data/hymnal-library.json`
- `data/ministry-books/library.sqlite`
- `data/ministry/recovery-bible/`
- `data/ministry/recovery-footnotes/`
- `data/ministry/life-study/`

Run `pnpm run prepare:library-bundle` before packaging. The command stages externally maintained source libraries and fails when a required library is missing. Backup SQLite files are excluded from the installer.

At runtime, `desktop/main.cjs` explicitly maps every packaged library to its resource path, together with the script locations (`AIOS_AI_ROOT`, `AIOS_HWMR_IMPORTER_SCRIPT`, `AIOS_INDEX_SCRIPT`), because `process.cwd()` in an installed application is not the repository. User-created Ministry imports are stored separately under Electron's user-data directory.

## Knowledge and indexing

Knowledge documents are organized by category, subcollection, and optional subject. The indexing pipeline extracts supported text, chunks it, builds embeddings and FAISS data, and records document metadata. Scanned PDFs pass through OCR before indexing. Production user knowledge and indexes live under the Electron user-data directory unless overridden.

Category, document, outline, viewer, and chunk-context browsing is answered locally by `server/knowledge.mjs` from the files the indexer writes, so the Knowledge screens work while the legacy API is stopped. Document detail reports its page, chunk, vector, and word counts from the stored artifacts, takes the embedding dimensions from each `.npy` header, and hashes the source file itself.

Key environment variables include:

- `AIOS_KNOWLEDGE_DIR`
- `AIOS_KNOWLEDGE_INDEX_DIR`
- `AIOS_KNOWLEDGE_TRASH_DIR`
- `AIOS_INDEX_PYTHON`
- `AIOS_INDEX_SCRIPT`
- `AIOS_INDEX_BUILDER`
- `AIOS_AI_ROOT` — the sibling AI root that locates `Knowledge/`, `Index/`, and the Python runtimes when the app is packaged

## Ministry import pipeline

- HWMR PDFs are transformed by `scripts/import-hwmr.py` into structured daily and weekly content. The importer reads `<AIOS_KNOWLEDGE_DIR>/Ministry/HWMR`, which is where Documents uploads land, so a PDF added through the app is picked up by the next refresh. `AIOS_HWMR_SOURCE_DIR` overrides that folder and `AIOS_HWMR_IMPORT_PYTHON` the interpreter used for it.
- Every refresh ends in a quality check of `passed` or `passed_with_exclusions`, and both publish. A file the reader cannot use is returned as an exclusion naming the file and the reason, which the app appends to the upload message; a refresh that throws reports the importer's own closing lines rather than a bare failure.
- Morning Nourishment references are stored so each one resolves on its own: a heading's prose lead-in ("In Revelation 20:1-4") is dropped, and a bare `8:11` inherits the book printed above it. `src/utils/bibleReferences.test.ts` requires every stored reference to link exactly one passage, which is the release gate for this library.
- Weekly hymns set as music are rebuilt from the two-up PDF sheets: syllable fragments are rejoined along the printed hyphen strokes, and chord rows — including the flat the sheet draws as `©` — are kept out of the lyric text.
- Recovery Bible text and study aids use the Recovery import scripts.
- Ministry Books are imported from the authorized single-file HTML archive into SQLite by `scripts/import-ministry-books-singlefile.py`.
- The Ministry Books importer distinguishes Content, Prefaces, numbered chapters, and appendices. Section display titles combine the role/number and actual heading.
- Scripture references preserve a return target so a reader can return to the same source position.

## Video training library

`server/video-training.mjs` serves a folder of training media rather than a parsed library, so a file copied in by hand appears exactly like one uploaded in the app.

- The folder is `AIOS_VIDEO_TRAINING_DIR`, defaulting to `<AIOS_KNOWLEDGE_DIR>/Ministry/Video Training`; `AIOS_MAX_VIDEO_TRAINING_MB` (default 2048) caps a single upload. In the packaged app `AIOS_KNOWLEDGE_DIR` already points at `data/knowledge` under the user profile, so the folder is writable and survives updates.
- `GET /video-training/library` reads the directory, keeps only allowed extensions, and returns `{ root, total, items }` newest-first with `media: 'video' | 'document'`. `POST /video-training/upload?name=`, `GET|HEAD /video-training/file?name=` and `DELETE /video-training/file?name=` cover the rest.
- Uploads stream the raw request body to disk — chunks are flushed to `<file>.part` and renamed on success — because `readForm` buffers the whole body in memory and a video is far too large for that. An interrupted or oversized upload leaves no half-written file in the library, and a second file with the same name is refused with 409 instead of overwriting.
- File reads honour `Range` requests (`206` with `Content-Range`, `416` past the end, suffix `bytes=-N` for the tail), which is what lets `<video>` seek without downloading the file first. `Content-Type` is taken from the extension map, not from the client.
- Every name is reduced to a single basename, checked against the extension allowlist, and re-checked to stay inside the folder before it touches the disk. `server/video-training.test.mjs` covers the allowlist, the traversal refusal, the range arithmetic, the size cap, and the duplicate name.
- Gateway routes that write the response themselves must `await` the handler inside the server's `try`. Returning the promise skips that `catch`, and the rejection becomes an unhandled rejection that stops the whole gateway.
- The client is `src/api/videoTraining.ts` (the upload uses `XMLHttpRequest` so the page can show real progress) and `src/pages/VideoTrainingPage.tsx`, whose sheet reuses the HWMR reading typography. The Ministry dashboard card sits beside HWMR and Hymns.

## Scripture and phrase search

Both reading libraries are served by the gateway from locally held text; neither depends on the legacy API or on embeddings.

- `/recovery-bible/concordance?q=&limit=&match=` reads the 66 chapter files under `AIOS_RECOVERY_BIBLE_DIR` through `server/recovery-bible.mjs`, which caches the ~31,000 verse lines in memory as a concordance. The default `match=words` requires each typed word to appear somewhere in the verse. `match=phrase` requires the whole string, in order. Omitting `match` keeps the historical behaviour, which is what the Recovery Bible and Ministry Books browsing pages rely on.
- `/ministry-books/search?q=&limit=&match=` queries the FTS5 table `block_search` over `data/ministry-books/library.sqlite` and ranks with `bm25()`. Word mode ANDs the individual words; `match=phrase` quotes the whole sanitized string as one FTS5 phrase, which is what gives adjacency. If the SQLite library is absent, the same handler falls back to the HTML source folders and applies the identical word/phrase distinction in code.
- Presentation Studio uses phrase mode in its **Find a phrase** boxes; the picked result seeds the verse basket or the section picker through a deferred-selection ref, because the chapter the result names may still be loading when it is clicked.

## Chat assistants

`server/agents.mjs` defines the three assistants the Chat page offers — General, Ministry, School — and `GET /agents` serves them to the side panel and the Agents page. Each has its own branch inside `POST /ask/stream` in `server/index.mjs`, so no chat answer travels through the legacy API any more; the untyped `proxyLegacyJson` that used to catch Ministry (and required `127.0.0.1:9655`, which nothing on this machine starts) is gone. `proxyLegacy` still bridges the paths the gateway has not taken over.

- **General** builds an inline prompt and never grounds: its metadata is always `grounded:false, source_count:0`, by design.
- **School** is the grounded template — `answerSchoolQuestion` retrieves from the School index and hands the model the excerpts plus their citations.
- **Ministry** has two layers, and the order matters. `useChat.ts` first tries the direct resolvers in `src/api/ministryAssistant.ts` — an exact reference like “John 3:16”, then the five libraries at once through `resolveUnifiedMinistryQuestion` — and any of them can answer without a model call. Only when none of them matches does the question reach `/ask/stream`, where `answerMinistryQuestion` retrieves from the Ministry category and grounds the answer in those excerpts. So a Ministry turn that used to end in “Lampstand could not complete this response.” now ends in a cited answer.
- The source chips under the composer (`All Ministry`, `Recovery Bible`, `HWMR`, `Life-Study`, `Ministry Books`, `Hymnal`) are sent as `ministry_source` and decide which documents the retrieval may read. The filter is a document-name predicate passed to `searchLocalKnowledge` as `documentFilter` and applied **inside** the scan, before ranking and truncation — filtering after `topK` let one text-heavy document fill the candidate list and starve every other chip, which is how the first version failed its own live test. Life-Study and Hymnal have no documents in the Ministry index (the hymns live in their own library, served by the direct resolver), so those chips answer honestly that nothing was found rather than quoting a Bible chapter.
- Two non-model replies are deliberate: when retrieval finds nothing the metadata is `grounded:false` with a message naming the chip that was selected, and when the local model is not running the answer lists the top citations instead of failing, with model `Local Ministry Library` — the same escape School uses.
- The **Web** chip is unrelated to the assistants and runs before them, so it needs a Tavily key in Settings → AI Services; without one it returns “Web search is not configured.”
- Two pages hand a question to an assistant instead of answering it themselves: School’s **Explain a lesson** and **Create notes from selected lesson** (`askSchool` in `src/pages/SchoolPage.tsx`), and the Knowledge viewer’s **Ask about this passage**. Both write `{ question, agentId }` to `aios-studio-chat-handoff-v1` and `navigate('/chat')`; the consumer in `src/App.tsx` switches the assistant, puts the text in the composer, and deletes the key. The consumer fires on `/` as well as `/chat`, because Chat is what `/` renders for profiles without Ministry access. It must not rely on `/` alone: for everyone else `/` redirects to the Ministry hub, which took both handoffs off the Chat page and dropped the drafted question.
- **New conversation** has one entry point that works on every page: `handleNewConversation` in `src/App.tsx`, reached from the side panel (`.new-chat-button`), the History page and the command palette. It navigates first, then decides — with no assistant available it only reports the missing connection, because `startNewChat` returns without a session and the old code toasted “New conversation started” anyway; with the active conversation still holding no user message of the selected assistant it keeps that session rather than prepending another identical `New conversation`. `useChat.ts` itself still creates unconditionally, so the assistant-change paths keep their behaviour. The button is disabled only while a response is streaming and carries a `title` naming why — it used to be disabled whenever no assistant was selected, which made it look dead with no explanation whenever the gateway was slow or a profile could not open Chat.
- Verified over HTTP without touching the running app: a throwaway gateway on `AIOS_API_PORT=9787` pointed at the real index with `AIOS_KNOWLEDGE_INDEX_DIR`, plus a second on 9788 with `OLLAMA_URL=http://127.0.0.1:14034 AIOS_PROVIDER_MODE=local` to prove the model-down path. `server/knowledge-search.test.mjs` keeps a fixture where twelve HWMR chunks outrank a single Matthew chunk, so the chip filter is covered without a model or an index.

## School lesson activities

The Quiz, Flashcards and Revision sheet views in `src/pages/SchoolPage.tsx` write their questions from the lessons the learner ticks, not from a fixed subject bank. The bank is still there as the fallback.

- `readKnowledgeLessons(category, document, sectionIds, config, { chunksPerLesson = 6, charactersPerLesson = 4000 })` in `server/knowledge.mjs` returns the concatenated indexed text of each selected section. `readKnowledgeOutline` and it are both wrappers around the internal `buildKnowledgeOutline`, so an outline section id is the same handle the activity page already holds; requested ids are de-duplicated and answered in book order. `chunk_id` is 1-based into the raw chunk array and a lesson reads `chunksPerLesson` chunks forward from its heading, because one printed lesson spans several chunks.
- `generateSchoolLessonQuestions({ category, document, sections, count }, config, fetcher)` in `server/knowledge-search.mjs` drops any lesson whose joined text is under 40 words, sends the rest — capped at 24,000 characters — to `generateTextWithProviders`, and always answers `{ questions, reason, count, lessonLabels }`. The requested count is clamped to 4–12 (the page asks for 10). `reason` is `no-lesson-selected`, `lesson-not-indexed`, `model-unavailable`, `model-output-unusable`, or empty, and the page turns each into its own sentence, so the fallback names its cause instead of failing silently.
- `POST /school/questions` in `server/index.mjs` is the only route; the client call is in `src/services/knowledge.ts`, because `src/api/knowledgeViewer.ts` is GET-only.
- A local model's JSON is *nearly* valid rather than valid, so `parseLessonQuestions` accepts fenced output and prose wrapped around the payload, repairs the two slips `qwen3:8b` was measured making — a stray extra quote before a key name, a comma before a closing brace — and then rejects any item without a real question, exactly four unique choices, and an answer resolvable as an index, a letter, or the choice text. Questions are de-duplicated and capped; a survivor with no explanation gets a plain one.
- The renderer shuffles choices and order (`randomizedQuestions`) before display, so **More Questions** re-rolls the same lessons and a repeated round is not in the same sequence. When generation returns nothing the page still starts the activity, on the subject practice set, and says why in the notice banner.
- Verified over HTTP against the real index: *Chapter-19 Fitting* and *Chapter-3 Technical Tearms* each produced five questions with no shared wording, in 20–22 s on `qwen3:8b`, and the second gateway with the model switched off answered `model-unavailable` in 1 s.

**The School card is paper, in both colour modes.** `.school-card,.school-recent,.school-library` in `src/styles/school.css` carry literal `background:#f4f1e9` / `color:#172033` with `#d7d2c8` borders, deliberately outside the token system, because a learner's worksheet is meant to read as a page rather than a dashboard — the same exemption the Bible and ministry-book readers have. Everything that is *not* paper on that page follows the tokens, which is why the header, summary tiles and library rows change with the theme while the cards do not. Anything added inside those three classes must be written for `#172033` ink on cream, not for the theme's `--text`; the quiz feedback colours (`#065f46`, `#9f1239`) and the notes buttons (`#ecfeff` on `#0e7490`) are chosen against cream and were measured there.

## Presentation projection

The audience output is one persistent window owned by `desktop/main.cjs`. It is created on the first take-live and reused for every later slide so nothing flashes open mid-meeting; the same document is reproduced in a browser popup when the desktop bridge is unavailable.

- Slide payloads are built in `src/utils/` (`bibleSlide.ts`, `hymnalSlide.ts`, `hwmrSlide.ts`) and each builder embeds its own `<style>` in the HTML it hands to the audience window. Footnote, hymn and HWMR typography therefore travels with the slide and cannot silently drift from the studio. Audience *layout* CSS is the exception: it exists in three places — `audienceLayoutStyles` in `src/components/PresentOnDisplay.tsx`, the inline `<style>` written by `desktop/main.cjs`, and `src/pages/PresentationPage.css` for the studio preview. Change all three together.
- **The formatted text window (`PortionEditor`).** `src/components/studio/PortionEditor.tsx` is the window both the **Custom portion** (`CustomSourcePanel.tsx`) and the **Announcements** (`AnnouncementSourcePanel.tsx`) panels write in, so one set of tools teaches the operator once. It is a `contentEditable` div driven by `document.execCommand`, so the formatting it offers depends on Chromium and the produced HTML is what the audience window is given, not a rich-text document model. Two document-level settings are applied once on mount: `styleWithCSS` so every command writes inline `style` rather than `<b>`/`<font>` tags (a style sheet travels to the projector, a tag may not), and `defaultParagraphSeparator` pinned to `p` so the window and the audience slide break lines identically. A toolbar press would take focus — and therefore the selection — away from the words being formatted, so `onMouseDown` is prevented on the buttons and the last in-editor `Range` is restored before a command runs. Three commands needed more than the editor offers: the **typeface** picker reads installed faces through `window.queryLocalFonts()` (a refused read still leaves the field usable — the name can be typed and Enter applies `localFontStack(name)`; the list is capped at 120 rows because a picker is only useful while it is being filtered), the **size** box is a multiple of the slide's own text while `fontSize` knows seven fixed sizes, so it marks the words `7` and rewrites the resulting `xxx-large` spans to `${multiple}em` (clamped `0.5`–`6`), and **highlight** re-reads every `span[style]` afterwards and sets its colour to `legibleInk(background)` with `data-markInk` so the words always read on the colour laid under them — and hands the ink back when the background is removed. Both pickers are commands, not readouts: they return to their own name after use, because a row of mixed faces or sizes must not claim to be one of them. The three alignment marks answer for the *line* under the caret (`alignOfCaret()` walks up to the first node with a declared `textAlign`, falling back to the slide's own), so a verse can stay left while a response is centered. Line spacing is the one property left to the whole slide, so it keeps a menu of its own; anything a host wants at slide level rides in the `slideTools` slot at the end of the toolbar (announcements put **Number the items** there), wrapped with the rule that parts it from the word tools so the pair wraps together. The window itself is `resize: vertical` from `190px` up to `70vh`, scrolling past that rather than pushing the rest of the panel away. Whatever is added passes through `sanitizeRichText()` in `src/utils/customSlide.ts` — a hand-written allowlist tokenizer, since the vitest environment has no DOM. It drops unknown tags *with their words* (so `<script>alert(1)</script>` leaves nothing), converts `<div>` to `<p>` and a legacy `<font face|size|color>` to a `<span>` of declarations, keeps only properties in `ALLOWED_STYLE`, and refuses anything containing `<`, `>`, `url(`, `expression` or `javascript:`. Two behaviours of real editor output shaped it: a quoted typeface arrives inside `innerHTML` as `&quot;`, whose trailing `;` split the name in half until the value is decoded *before* the declaration split; and `innerHTML` already encodes `&nbsp;`, so the rich-text path escapes only `<` and `&` that begin no entity, or the projector prints the literal `&nbsp;`. `customSlideRules()` is injected as a `<style>` into the editor itself, which is why the window reads the way the slide will; the same rules give every paragraph the slide's own serif at weight 400 so inline bold or size always stands out. Slide-level state is only `align` (`left`/`center`/`justify`) and `spacing` (`normal`/`roomy`/`open`) — the earlier slide-wide typeface and emphasis defaults were removed because each word now carries its own. The console's shortcuts must not fire while text is being written, so the global keydown handler in `src/pages/PresentationPage.tsx` also returns for `event.target instanceof HTMLElement && event.target.isContentEditable` (`B` would otherwise blank the projector mid-sentence).
- **Announcement slides.** `src/utils/announcementSlide.ts` turns the same window markup into a slide: `richItems()` in `customSlide.ts` splits it into one item per block or `<br>` (a leading bare text node is wrapped into a `<p>` by `sanitizeRichText`, so a loose first line still counts as its own item), and each item becomes an `<li>` carrying only the line's own `text-align`. The marker comes from the slide, not the words — **Number the items** chooses `<ol>` over `<ul>` for the whole list — so a date made bold never loses the numbering the notices are read by. The heading and closing line are plain escaped text; the list is centred on the screen while each item is left-aligned, and a long list scrolls on the projector with the heading held in place.
- Scripture references are rendered as `<a class="verse-link" data-book data-chapter data-verse data-verse-end>` by `src/utils/bibleLinks.ts`, which is shared by the Bible slide and HWMR slide builders. A small script appended to the audience document intercepts the click and calls `window.lampstandAudience.selectVerse(reference)` — exposed by `desktop/presentation-preload.cjs`, sent as `lampstand:presentation-verse`, and re-emitted by the main process as `lampstand:audience-verse` to the studio window. The popup path uses `window.opener.postMessage({ type: 'lampstand:audience-verse' })` instead. The studio resolves the reference against the local Recovery Bible library and projects the verse as an interlude; the queued slide and run of show are untouched, and taking any slide live clears the interlude.
- `PresentOnDisplay` asks the main process for the display list when the picker mounts and again when the re-scan button beside it is pressed, so a projector connected after launch becomes selectable without restarting the app. The studio's **Preview** group renders only the picker (`AudienceScreenPicker`); the full card — picker plus its own take-live button — is what the Bible and School pages use. Preferences (screen, title, theme, text size, transition, fade speed and the chosen room speaker) are stored under `lampstand.presentation.prefs`, resolve on the next take-live, and reach the audience window as `audioSinkId` plus the speaker's name — see **Audience audio, and why a device id does not travel**.
- **The control rail is icon-only, and the theme fights it.** `src/styles/theme-overrides.css` ends with `.workspace-panel button { min-height:36px; padding-inline:13px }` — specificity `0,1,1`, which beats a single class. An icon button styled with one class therefore gets 13px of side padding on a 32px box and its glyph is squeezed to a 4px sliver, and any colour its own class sets loses to the same rule. Every rail control is therefore addressed with two classes (`.console-bar .icon-action`, `.present-on-display button.present-detect`). This is not visible in a unit test: the vitest environment has no DOM, so the rail is verified against the running dev server by measuring each control's box.
- **Settings is icon-only too, and keeps the same rule.** `src/styles/settings.css` defines `.settings-page .icon-btn` — the two classes are what out-rank the workspace button rule above — as the single 30px square used wherever a glyph is unambiguous: check/refresh, copy, repair, remove, reload, the AI services power switch, and the accent colour dots. Each one carries `title` and `aria-label` with the exact words it replaced, because the tooltip is now the label; the manual tells operators to hover or tab to read a control. Actions that need a version number, name a person, or destroy data keep their words (**Download version …**, **Restart and install**, **Reinstall this version**, **Reset personal data**, **Switch to …**, **Approve & sync this computer**, **Save provider choice**), and destructive glyphs keep the red treatment through `.icon-btn.remove`. Everything else was pulled onto one row: provider status became wrapping chips, the four cloud-key cards and three model fields went to a grid, the provider-mode radios lost their second line, and the role builder's create button moved to the end of the workspace row instead of spanning the panel. Row heights are measured live over CDP (`settings-panels.mjs` prints each `.settings-panel` box) because no test can see them.
- **Settings is four labelled groups on one grid, and its type fights the theme.** `src/pages/SettingsPage.tsx` renders the panels in reading order — *Access and devices*, *Services and models*, *Appearance and reading*, *Data and updates* — each introduced by an `<h2 class="settings-section-title">` that is itself a child of `.settings-grid` and spans the row. Nothing is reordered in CSS any more: `settings-order.css` was deleted with it, and the only spans left are `grid-column:1/-1` for the panels whose contents are themselves multi-column grids (Users & Access, Remote family access, AI Services, AIOS API), plus `span 3` for the two paired groups at `min-width:1800px`, where the grid is `repeat(6,minmax(0,1fr))`. Below that width the same DOM produces the two-column page. `theme-overrides.css` sets `.settings-grid{align-items:start}`, so a short card never stretches to its row and panel *heights* decide the tiling as much as widths do. The same theme file pins every `<small>` in a workspace panel to `12px!important` and every control to `13px!important`, which is why the Settings type floor is declared with `!important` and two classes (`.settings-page small{font-size:13px!important}`); the scale is 17px panel title, 15px decision label, 13–13.5px body, and no rule under 13px. Both are verified live over CDP at 2560/1800/1366 — `settings-columns.mjs` prints each panel box, `settings-typed.mjs` also lists any element whose own text renders below 13px and any descendant whose text is clipped — because no test can see them.
- **The Church hub borrows the Settings layout language.** `src/pages/ChurchPage.tsx` splits into three labelled groups on one column — *Status*, *Tools*, *Recent activity* — each an `<h2 class="church-section-title">` that is a direct child of `.church-page`. The title is a flex row whose `::after` is the rule line, so the group's one action (**View all**) rides at the right end of it; that is why the recent-activity panel no longer carries its own header. The four tool cards are the reason the grid is `repeat(2,…)` with `repeat(4,…)` at `min-width:1650px`: at the old three columns the fourth card sat alone under a two-thirds hole. Note that `.church-page{max-width:1320px}` in `src/styles/church.css` has no effect — `theme-overrides.css` ends its responsive-measure block with `max-width:none!important`, so every workspace page is full-bleed and must tile for 2312px as much as for 1118px. The same theme file pins `<small>` to `12px!important`, so this page answers with `.church-page small{font-size:13px!important}` — plain 13px declarations lose to an `!important` no matter how specific they are. The scale is 16px status value, 13px label, chip, meta and section title. Verified live over CDP — `church-verify.mjs` prints each group's boxes and every element under 13px, `church-sweep.mjs` walks 420→1700px reporting cards-per-row and clipped status values, and `church-rows.mjs` injects two mock activity rows into the DOM before measuring, because with the operator's records empty the list renders nothing and its `<small>` escapes the sub-13px audit entirely.
- **Media library.** `server/presentation-media.mjs` serves a second, user-owned folder (`config.presentationMediaDir`, default `<knowledgeDir>/Presentation Media`) over `GET /presentation-media/library`, `POST /presentation-media/upload?name=`, `GET|HEAD /presentation-media/file?name=`, `DELETE /presentation-media/file|group?name=` and `POST /presentation-media/deck?name=`. Names are sanitised before they touch the disk (`safeRelativePath`: at most three `/` segments, no leading dot, no Windows-illegal character, 120-character stem, extension allowlist) and every read re-checks that the resolved path is still inside the root. Files stream with full HTTP Range support (`206`/`Content-Range`, `bytes=-N`, `416`), which is what lets the projector seek inside a large video; `server/media.mjs` has no range handling and is not used for this. Like the video-training routes, the streaming route `await`s inside the gateway's `try` and only then `return`s — returning the promise would bypass the catch and kill the Node process. SVG is excluded on purpose: an uploaded vector file is an HTML document that would run inside the projector window. **Go-live check.** `mediaProjectionWarning()` in `src/components/PresentOnDisplay.tsx` sends one `HEAD` for the file the slide is about to show — the current page, resolved with `deckSlidePath` for a deck — before `presentOnSavedDisplay` runs, on every path that puts media on air (**Take live**, **Take preview live**, previous/next live, Ctrl+Enter, the deck and PDF page arrows, and the return from a verse interlude). Only a `404` raises the console warning; a refused or failing request stays silent, because a stopped gateway must not be reported as a deleted file. The slide still goes live — the message names the tab that restores the file and the operator decides what to do next.
- **Media slides.** `src/utils/mediaSlide.ts` builds image, video, audio and PDF slides from a library path and always emits the *absolute* gateway URL, because the audience document is a `data:` URL and cannot resolve a relative one (a probe confirmed a `data:` document may still load `http://127.0.0.1:9656` media). Video is projected without `controls` — the studio drives the player through IPC. Height comes from `var(--media-max, 66vh)` so the same slide fits the small studio preview.
- **Zoom on a still frame.** `MediaSlideSource.zoom` is carried into the html as an inline `--media-zoom` custom property, and the slide's own style sheet scales the stage (`transform:scale(var(--media-zoom,1)); transform-origin:center`) — full-bleed stages get `overflow:hidden` so the enlarged frame is cut off at the projector edge instead of growing the document. `clampZoom()` pins the value to `MIN_ZOOM`/`MAX_ZOOM` (`1`–`4`) in quarter steps and rounds to two decimals, because the number is interpolated straight into a `style` attribute; exactly `1` prints no attribute at all, so an unzoomed slide keeps its previous byte-for-byte html. Changing zoom regenerates the html and re-projects with `transition:'none'` (the same in-place path `stepMediaPage` uses) — **there is no new IPC command**, and the audience document is never reloaded, so only the picture moves and the sound keeps playing. Zoom is offered for images, PDF pages and deck slides only: re-projecting a live video would restart it.
- **The console preview never plays media.** `PresentationPage.tsx` builds the preview from the same html the projector gets, so the queue item's own `autoplay` flag is stripped before rendering (`mediaSlideHtml({ ...active.media, autoplay: false })`) — otherwise a cued song started the moment it was selected, in the operator's room. The Media tab's option row is scoped to the active filter (`all` shows the union): fill-screen for image/video, autoplay/repeat/silent for video/audio, first page for documents, and nothing at all for the PowerPoint filter, which has no per-file option to set.
- **PowerPoint.** `server/presentation-decks.mjs` shells out to `scripts/export-presentation-deck.ps1` (PowerPoint COM, one PNG per slide plus the title text) and returns `{ group, total, pages[] }`; the converter's single JSON line is parsed there, `422` carries the "save it as a PDF" instruction when PowerPoint is missing, and `504` when the conversion is killed. The script path arrives as `AIOS_PRESENTATION_DECK_SCRIPT` and ships through `extraResources`.
- **Web output.** `ipcMain` handler `lampstand:open-presentation-web` loads any `http(s)` URL into the same audience window. That window uses `partition: 'persist:lampstand-audience'`, so a sign-in done once survives to the next meeting; `configureMediaPermissions()` grants `media`, `mediaKeySystem` and `fullscreen` on that partition only, and `autoplay-policy=no-user-gesture-required` lets a take-live video start without a click. `lampstand:presentation-command` runs fixed, key-allowlisted snippets (`play`, `pause`, `toggle`, `restart`, `mute`, `unmute`, `volume`, `fullscreen`, plus `reload`/`back`/`forward`) through `webContents.executeJavaScript`, which also reaches cross-origin players such as YouTube; the volume value is clamped to `0..1` and interpolated only as a number. `lampstand:presentation-capture` (`capturePage`) and `lampstand:presentation-input` (normalised `move`/`click`/`double-click`/`wheel` and an allowlisted `key`/`insertText`) drive the audience monitor used for login pages — the studio never sees or stores a password.
- **The staged window is where a page is worked before it is aired.** `lampstand:stage-web` opens (or reuses) a second window in the *same* `AUDIENCE_PARTITION`, so a sign-in made on the operator's screen is the sign-in the projector already has; `lampstand:stage-state` reports `{ open, url, title, loading, canGoBack, canGoForward }` and `lampstand:stage-command` accepts only `reload`/`back`/`forward`/`close`. The stage handler `await`s `webContents.loadURL()` before answering, because the console reads the state back immediately and a name for the page is only worth showing once the navigation has committed; a rejected load is swallowed and still answers `false` rather than throwing, since a throw inside an `ipcMain` handler leaves the renderer's promise unsettled and the console hangs instead of failing. `WebSourcePanel` polls `stageState()` every 1.2s while a stage window is reported open, and re-reads it right after opening, closing or reloading — the window is driven by the operator directly, so the studio can only observe it. **Take it live** is offered only when the staged URL is `http(s)`; it reuses `presentWebSource`, so the projector loads the address the staged window ended on (after a login redirect, that is the logged-in page, not the sign-in page). The console keeps `webOnAir` for a page taken outside the queue: the **Live** row then reads `Web: …` / `off the run of show` with a **Return** button, and `takeLive`, `blankOutput` and the verse interlude all clear it. `presentationWindow.on('closed')` also emits `lampstand:audience-closed` to the studio, because a projector shut with Alt+F4 or a pulled cable must not leave the console naming a slide on a dark screen.
- **Audience audio, and why a device id does not travel.** `applyAudienceAudio(output, payload)` is the one path that touches the projector's sound: it sets `volume` on every `video`/`audio` to the console's last `mediaLevel` (falling back to `DEFAULT_MEDIA_LEVEL`), and, when the payload carries a speaker, runs `audienceSinkScript()` — an async snippet that finds the device *by label* in the window's own session, then re-applies `setSinkId()` to every player past and future through a `MutationObserver`. Matching on the label is not a style choice: Chromium salts `MediaDeviceInfo.deviceId` per browsing session, so the id chosen in the studio is unknown to the audience partition and `setSinkId()` rejects it with `NotFoundError` (measured: the same speaker is `52537d0d…` in the studio and `e1c5f712…` in the projector, both named *Speakers (VB-Audio Virtual Cable)*). `audioOutputName()` in `src/utils/audioRouting.ts` resolves the stored id to its label in the studio, and `presentWebSource` sends it as `audioSinkName`; `default` and `communications` are the two ids every session shares and skip the lookup. A slide document cannot be steered at all: a top-level `data:` navigation is not a secure context in Electron, so `navigator.mediaDevices` is `undefined` there (measured, `isSecureContext === false`), which is why only a projected web page carries the room speaker and a media slide plays on the projector's Windows default output.
- **Audio routing.** `src/utils/audioRouting.ts` lists input and output devices, routes an `HTMLMediaElement` with `setSinkId()`, and opens a monitor path (`getUserMedia` → hidden `<audio>` → chosen sink → `AnalyserNode` meter). Nothing is recorded; the path exists only while the button is engaged.
- **Run of show, from the keyboard.** Each queue row is a `<button>` that selects the slide for preview, and its four actions are `role="button"` spans inside it (`QueueAction` in `src/pages/PresentationPage.tsx`) — real nested buttons would be invalid inside a button, so the spans carry `tabIndex` and their own `onClick`/`onKeyDown`. Two Chromium behaviours make this harder than it looks, both measured against a headless page with trusted CDP key events: **Enter on one of the spans makes the browser click the row button as well** (a simulated click, `detail === 0`, dispatched even though the keydown was `preventDefault`ed), so the row's `onClick` ignores exactly that combination with `isActionKeyEcho` — `detail === 0` while the focused element is not the click target. Space does not produce the echo, and a mouse click always reports `detail >= 1`, so ordinary clicking is unaffected. And **moving a focused DOM node blurs it**, which is what a keyed list reorder does in React, so `QueueAction` re-focuses its own node in a `requestAnimationFrame` after the state update commits; the operator can hold `Enter` and keep walking one slide up or down. A keyboard **Delete** has nothing left to refocus — its node is gone and `focus()` on a detached element is a no-op — so focus returns to the top of the page.

## Voice Studio (optional local voice provider)

[Voice Studio](https://github.com/debpalash/VoiceStudio) is a separate Electron application the operator installs themselves. It is **not** bundled: it is AGPL-3.0, so it stays an external localhost service on the same footing as ComfyUI, WanGP and Ultimate TTS Studio. Lampstand only talks to it over `127.0.0.1`.

- `server/config.mjs` resolves `voiceStudioUrl` (`VOICESTUDIO_URL`, default `http://127.0.0.1:3900`), `voiceStudioExecutable` (`VOICESTUDIO_EXE`, then `%LOCALAPPDATA%\Programs\VoiceStudio\VoiceStudio.exe`, then `%PROGRAMFILES%\VoiceStudio\VoiceStudio.exe`), `voiceStudioTranscriptionModel` (`whisper-1`), `voiceStudioSpeechModel` (`omnivoice`) and `voiceStudioSpeechVoice` (`default`).
- `server/services.mjs` lists it as the sixth `definitions()` entry — `{ id: 'voicestudio', label: 'Voice Studio (speech and transcription)' }` — probed with `GET /health` on the same 1800 ms timeout as every other provider. Because the Settings → AI Services grid and the first-run wizard map over `providers`, the tile and the wizard line appear without any UI change; `startAiServices` launches the installed executable through the same detached-spawn branch Ollama uses.
- Transcription reuses the contract rather than adding an adapter: `transcribeWithProviders` builds `localTranscriptionTargets` and tries Voice Studio's `/v1/audio/transcriptions` before the bundled Whisper server, so `WHISPER_URL` no longer has to be repointed. The provider that actually answered is returned lowercased in `provider` and shown as *Processed by voice studio* in Language Tools.
- Speech is the one place a real adapter was needed. `runSpeechJob` selects `runVoiceStudioSpeech` (`POST /v1/audio/speech`, mp3) when `/health` answers, otherwise `runGradioSpeech` keeps the Ultimate TTS Studio sequence. Voice Studio returns bytes instead of a Gradio file URL, so the mp3 is written to `<mediaJobsFile directory>/media-audio/<job id>.mp3` and `proxyAudioFile` streams it from disk; the `providerUrl` fetch path is untouched.
- `audioFile` is stripped by `publicJob` alongside `providerId` and `providerUrl`, so the absolute local path never leaves the gateway — the remote-access routes would otherwise expose it. `/media/providers` reports `speech.available` as Gradio **or** Voice Studio, which is what turns the Media Studio *Speech* chip **Ready** without any frontend change. `/language/providers` gained a `voiceStudio` entry that feeds the fourth status chip; `language-provider-status` switched to `repeat(auto-fit,minmax(190px,1fr))` so four chips tile without phantom tracks at any width.

**Verified capability limits.** On the operator's install (VoiceStudio 0.5.7, active engine `k2-fsa/OmniVoice`, ASR `whisperx` / faster-whisper-large-v3, RTX 2080): English speech is correct and scales with input length (a three-sentence paragraph produced 8.56 s of audio that transcribed back verbatim). Malayalam, Tamil, Hindi and Chinese produced 0.8–1.8 s regardless of input length and transcribed back empty or wrong, so the OmniVoice build does **not** synthesise those scripts usefully despite the "600+ languages" display name. That is why pronunciation stays on Windows voices plus the Microsoft online fallback (`server/pronunciation.mjs` is untouched), and why Media Studio speech keeps its English guard even though Voice Studio's OpenAI endpoint accepts any `input`. Transcription is genuinely multilingual on this engine and is not limited to English.

`server/services.test.mjs`, `server/providers.test.mjs` and `server/media.test.mjs` cover the sixth provider, the Voice-Studio-first ordering with its Whisper fallback, and the Voice Studio speech job (file written, path stripped from the public job). Live verification ran against the dev rig: the gateway reported `voicestudio` available, a queued speech job completed in about two seconds through `/media/generations` and served from `/media/audio/:id`, and the same file transcribed back word-for-word with `provider: "voice studio"`. Generated artifacts under the dev Electron user-data directory were deleted afterwards.

## System resources readout

The side panel's **This computer** block reads `GET /system/resources`, answered by `createResourceSampler()` in `server/resources.mjs`.

- The gateway runs inside Electron's main process, so the desktop host injects its own footprint instead of bridging it over IPC: `createAiosServer({ readAppMemory })` in `desktop/main.cjs` sums `app.getAppMetrics()`'s `memory.workingSetSize`, which is **kilobytes** and must be multiplied by 1024. That is the whole application rather than one process. Without the injection the sampler falls back to `process.memoryUsage().rss` and the row is labelled **Gateway service**, which is what a plain-browser run shows.
- GPU numbers come from `nvidia-smi --query-gpu=name,memory.used,memory.total,utilization.gpu --format=csv,noheader,nounits`, run with `execFile` and no shell on a 2.5 s timeout. The result is cached for 4 s, and a failure is cached for the same window so a machine without the driver pays for one spawn per cache period rather than one per poll. A blank utilisation column stays `null` — some drivers omit the field rather than report zero — and `parseNvidiaSmi` is exported so `server/resources.test.mjs` can cover multi-card output, `[N/A]` and `ERROR: no devices found` without spawning anything.
- `os.loadavg()` returns `[0,0,0]` on Windows, so the CPU percentage is derived from the difference between two `os.cpus()` tick samples (idle plus `irq` over total). The first read of a session has nothing to compare against and reports `null`; the panel shows *measuring* rather than a fabricated zero.
- The route is unauthenticated like `/health` — the gateway binds 127.0.0.1 and answers CORS only — and returns the snapshot in one object so the panel never needs a second request per row.
- The client is `src/hooks/useSystemResources.ts` (5 s poll, skipped while `document.hidden`, re-read on focus and visibility change) and `src/components/Sidebar/SystemResourcesPanel.tsx`. A failed read clears the figures on purpose: a number that stopped moving looks like a quiet machine. When the card is not NVIDIA the panel still names it, from `WEBGL_debug_renderer_info`, and draws no bars.

The panel itself is `src/components/Sidebar/Sidebar.tsx`: `workspaceGroups` holds the four headings and their destinations, each gated link carries the `WorkspaceId` that filters it through `canAccess` (Settings and Help & Guides carry none, so every profile sees them), and the assistant picker plus conversation list render only when the route is chat. `.sidebar` is a fixed header, a scrolling `.sidebar-body` and a pinned `.sidebar-footer`; the destination list is the flexible part (`flex:1 1 auto; min-height:96px`) so it takes the scroll when the window is short and the chat blocks and the readout never disappear. `theme-overrides.css` re-declares the nav link metrics, so sizing changes belong there, and the new blocks use theme tokens (`--border`, `--panel-light`, `--text`, `--text-muted`) so both themes follow without extra rules.

## Help & Guides layout

`src/pages/HelpPage.tsx` renders header → guide buttons → document → quick tips, so the guide is the first thing on screen instead of sitting behind a wall of cards. The tips are one `quickHelp` array whose entries carry a `group` taken from `tipGroups`; the section is folded by default and `tipQuery` filters on title plus text, revealing the list while it is non-empty — the open state is derived, so clearing the box returns to whatever the button last chose.

`.workspace-panel>*` in `theme-overrides.css` forces every workspace to `max-width:none`, so a reading measure cannot be set on `.help-page` itself. It is applied to the four children instead (`width:min(100%,1120px); margin-inline:auto`).

## Appearance and theme tokens

`src/utils/themeMode.ts` owns the theme attribute, and `applyTheme(preference)` is the only way to write it. It resolves the stored choice (`system` | `light` | `dark`) against the device scheme and puts the **resolved** mode in `data-theme`, the **stored** choice in `data-theme-preference`; the four former assignment sites (`src/main.tsx`, `src/App.tsx`, and the save effect and `selectTheme` in `src/pages/SettingsPage.tsx`) all call it. `applyTheme` also registers one `matchMedia('(prefers-color-scheme: light)')` listener, so a "Use device setting" profile recolours the moment Windows changes its mode, with no reload; an explicit Light or Dark choice ignores the device. Anything unrecognised in storage falls back to `system`. `data-theme` therefore only ever holds `light` or `dark` — no rule may be written against `[data-theme="system"]`, and the `@media (prefers-color-scheme: light){ :root[data-theme="system"]{…} }` duplicate that used to sit in `variables.css` has been deleted so the light tokens have one home.

This is a recent fix, and the bug it closed explains most of the colour complaints. While `data-theme` carried the raw preference:

- every repair rule written as `:root[data-theme="light"] …` — most of `theme-overrides.css` — was **inert for a "Use device setting" user on a light machine**. Only `variables.css` handled that case, through the media block above. So a page that hard-coded dark-mode colours looked broken in light, and a page whose colours were "fixed" only in `theme-overrides.css` was still broken for the majority of operators, who leave the mode on device setting.
- the dark-only accent overrides (`:root[data-theme="dark"][data-accent="blue"]` and friends, `variables.css:73-78`) never matched in system mode either, so a device in dark mode with a chosen accent got that accent's **light** value — Gold went back to `#8a5a00` on a navy panel.

Verify the resolution itself with `C:/tmp/dev-rig/theme-resolve-check.mjs`, which emulates each device scheme, reloads, then flips the scheme *without* reloading to prove the listener fires, and finally calls `applyTheme` for all three explicit choices. It reads and writes only the live attributes — the stored settings string must be identical in the `before` and `after` blocks.

The rule that follows is that page CSS carries no colour literals: it uses the tokens (`--bg`, `--panel`, `--panel-light`, `--surface-muted`, `--surface-raised`, `--border`, `--text`, `--text-muted`, `--primary`, `--primary-hover`, `--primary-contrast`, `--primary-soft`, `--primary-border`, `--success`, `--warning`, `--danger`) and both themes fall out of `variables.css`. Where a literal is unavoidable — the `<mark>` pair `#fde68a`/`#172033` in `knowledge-search.css`, the reader paper, the projector slide — it is one that reads the same in either mode.

Three token conventions are load-bearing:

- `--primary` is a *fill and indicator* colour. As small text on a light panel it is marginal (`#635bff` measures 4.46:1 on `--panel-light`, 4.15:1 on `--surface-muted`), so text that is a link or a selected label uses `var(--link, var(--primary))`: `--link` is declared only in the light block at `variables.css:55`, and an unresolved custom property falls back, which gives cyan in dark and `#1d4ed8` (5.9:1) in light from one declaration.
- Text that sits on `--primary` uses `--primary-contrast`, never `#fff`. The side panel's **New conversation** button measured 3.41:1 with white on cyan; with `--primary-contrast` it is dark ink on cyan in dark mode and white on indigo in light.
- The light theme carries its own `--success:#065f46`, `--warning:#92400e`, `--danger:#b91c1c`, and `--text-muted:#5d6680`. These are set by the tint, not the token alone: a status chip is `color-mix(… 14%, var(--panel))` behind the same hue, so `#b45309` on its own amber wash measured 4.14:1 at 12px and every *Pending* row on the Documents page failed. `--text-muted` has to clear 4.5:1 against `--surface-muted` (`#eef1f7`), which is the side panel's background, not just against white.

Cascade order decides which file wins. `src/styles/index.css:29` imports `theme-overrides.css` eagerly, while each page imports its own CSS from its page module, so **page CSS lands later and beats a non-`!important` rule in the theme layer** — that is how `.documents-table td strong` survived the light layer's `.documents-table td`, and why the sidebar's own `Deep Navy & Ice Blue` block in `sidebar.css` overrode the theme file's `.sidebar{background:var(--surface-muted)}` and left light panels under hard-coded ice-blue labels. A theme repair that must win needs either `!important` or the page's own file.

Contrast is verified against the running app rather than by reading CSS: `C:/tmp/dev-rig/page-contrast-audit.mjs <theme> <scheme> <routes>` walks the router over every route through CDP, composites each visible text node against its painted ancestors, and reports the WCAG failures at the 3:1 (large/bold) and 4.5:1 floors. Two traps in that rig are worth repeating: `Emulation.setEmulatedMedia` only works with `features:[{name:'prefers-color-scheme',value:'light'}]` — the older `{media:'…'}` string is accepted and does nothing, which is what made an earlier pass report dark numbers for a light device — and Chrome serialises a `color-mix()` background as `color(srgb 1 1 1 / .88)`, so the parser must read decimals (`[\d.]+`) or the composite silently becomes black and invents failures.

As of this pass the audit has been re-run app-wide in light with the resolution fix in place, which matters because the repair layer now reaches device-setting operators for the first time. `/knowledge`, `/knowledge/search`, `/documents`, `/school`, `/ministry`, `/ministry/video-training`, the Church pages, `/help` and `/updates` report **zero** failures in both resolved modes. Remaining light failures, worst first: `/hymnal` 3237 (the catalog list), `/ministry-books` 509, `/recovery-bible` 33, `/agents` 15, `/ministry/hwmr` 13, `/presentation` 12, `/chat` 8, `/media` 7, `/settings` 5, `/language-tools` and `/history` 4, `/life-study`, `/church` and `/church/posting-history` 1. The stylesheets still carrying literals are `hymnal.css`, `media-studio.css`, `settings.css`, `agents.css`, `chat`/`composer.css`, `presentation-*.css` and `hwmr.css`; the reader accent on `recovery-bible`/`life-study` fails in **both** modes, because cyan verse labels sit on cream paper. The audit's `system` invocations are obsolete: since the attribute is resolved, `page-contrast-audit.mjs light light` and `page-contrast-audit.mjs dark dark` are the two device cases, and passing `system` as the theme now selects a mode that CSS no longer defines.

## Typography floor

No label in the operator UI renders below **12px**. This is a settled convention rather than a runtime guard: a one-off pass rewrote every declaration under the floor in `src/styles/**`, `src/index.css`, `src/components/PresentOnDisplay.css`, `src/components/studio/StudioPanels.css` and the three `src/pages/Presentation*.css` files. Anything new should be written at 12px or above.

Three spellings carried sub-floor text and all three need checking — `font-size:11px`, the `font:` shorthand (`font:700 11px/1 Inter,sans-serif`), and fractional rems. The rem form is the easy one to miss: `.6rem` is 9.6px, and a pattern written for two-digit fractions (`\.\d\d rem`) silently skips the single-digit ones.

Two rules in `theme-overrides.css` sit above the page styles and explain why some sizes look inconsistent: `.workspace-panel :where(button,input,select,textarea){font-size:13px!important}` pins every control's own text to 13px regardless of its page rule, and the same block forces `max-width:none` on workspace children, which is why a reading measure has to be applied to a page's children rather than the page (see *Help & Guides layout*).

Audience typography is deliberately outside the floor. Slide CSS is built in template strings — `src/components/PresentOnDisplay.tsx` and `src/utils/announcementSlide.ts`, `customSlide.ts`, `hwmrSlide.ts`, `hymnalSlide.ts` — and sizes itself in `em` so the **AA** audience control scales the whole slide. The two reader pages that own their size are `--bible-font-size` (`src/pages/RecoveryBiblePage.tsx`, stored as `aios-bible-font-size`) and `--hwmr-reader-zoom` (`src/styles/hwmr.css`, applied through `calc(18px * …)`).

Raising the minimum exposed two layout problems that were previously hidden by small text. `.resource-row` in `sidebar.css` is `28px minmax(0,1fr) 34px auto`: the value column ("6.6 of 8 GB") is wide enough to starve the name column, so the old `30px / 46px / 8px gap` split left 34px for a processor model. And the **Favorites** filter chip in Media Studio was clipped to "Favc" because hymnal.css defines a global icon-only `.favorite{width:40px;height:40px}` that the chip's class also matched — `media-studio.css` now overrides the width and lets `.media-history-filters` wrap. A bare `.favorite` class name is therefore unsafe outside the hymnal grid.

Verification is a Chrome DevTools Protocol walk of each route that reads computed `font-size` on every element with its own text (including form controls), plus `scrollWidth`/`clientWidth` and the sidebar footer's bottom edge against the viewport, at 2560×1369, 1920×1080, 1440×900, 1366×768 and 900×700. Screen-reader-only elements (`.sr-only`, 1px boxes) show up as clipped and should be ignored.

## Development

```powershell
pnpm install
pnpm run start:local
pnpm run dev
```

Open `http://localhost:5173`. Put local overrides and secrets in `.env.local`; never commit it.

The browser shows the console but not the desktop surface: `window.lampstandDesktop` is injected by
`desktop/preload.cjs`, so the projector window, media transport, staging and audio routing are absent
there. `pnpm run desktop:dev` opens a real app window that hot-reloads, with no build, installer or
version bump. It starts Vite on `127.0.0.1:5173`, waits until it answers 200, then launches Electron
with `LAMPSTAND_DEV_URL` set; `desktop/main.cjs` skips its own static `dist/` server and loads that
URL instead. Closing the window stops Vite.

That window reads the gateway on 9656 like any other build, and it uses the same user-data folder as
the installed app, so profiles, queue and annotations are the real ones. If the installed app is still
running it already owns 9656, and the dev window silently reads that older server — the script warns
about this, because a server-side edit then appears to do nothing.

Useful verification commands:

```powershell
pnpm run lint
pnpm test
pnpm run build
pnpm run verify:release
```

## Windows packaging and updates

Create an installer with:

```powershell
pnpm run desktop:installer
```

This stages the reading libraries, builds the frontend, and creates an NSIS x64 installer in `release/`. Updates are published through the configured GitHub Releases repository with the installer, blockmap, and `latest.yml`. The Electron updater downloads only after the user requests it.

`build-assets/installer.nsh` adds two pages after the installation folder is chosen: the optional AI components, and **Existing data on this computer**. The data page offers Keep (selected) and Erase; `customInstall` only touches `%APPDATA%\lampstand-studio` when the erase radio is checked *and* the confirmation `MessageBox` answers Yes. The `MessageBox` carries `/SD IDNO`, so a silent `/S` run keeps data without any prompt. The folder name is Electron's `app.getPath('userData')` value, which follows package.json `name` (`lampstand-studio`) rather than the product title, so a rename of `productName` in the future also means updating `LAMPSTAND_DATA_DIR`.

## Data protection and backups

Keep packaged reference libraries immutable. Store member-created knowledge, progress, annotations, conversations, media history, and imports in user-data locations. Backups should include those user-data folders and knowledge indexes; downloadable AI models may be omitted.
